## A. エンジン・プラットフォーム

**Q2.** 想定エディション: Windows 通常版 (DLsite)、ci-en 版、体験版 (Windows/Web)、Steam 版と Steam 健全版、Android。Mac は?
**A.** mac はデバッグ用途のみ。それ以外は全て提案通り。

**Q3.** 画面サイズ: tale の 1280x720 固定 + transform: scale か、xqueens のリサイズ耐性か。
**A.** 実効解像度が低くなる懸念があるため scale フィットは NG。ただし xqueens のフォントサイズ処理は不便ではある。ウィンドウサイズが大きくなった際に相対的に文字サイズが小さくなるのも困る。1280x720 を最低サイズの基準にしてそこから Electron 側の拡大機能を使うとか? でもそれだとブラウザ側で困りそうな気もする。アイデアをいただきたい。
→ 提案は 01_architecture「画面サイズ」(論理ステージ + CSS zoom)。

**Q4.** リポジトリ構成: xqueens と同じ 4 分割か、モノレポか。
**A.** モノレポで OK。秘匿アセットだけ symlink にしましょう。ただし、マスターデータのエディションごとの出し分けは必須。

**Q5.** eslint / prettier / vitest / Node 22 は xqueens 準拠で。
**A.** OK だけど、エンジン・ツールともにバージョン上げれるならあげよう。

**A.** 一旦提案通りで進めてみたいですが、実装を見て別設計をお願いするかも。

**Q13.** 1 効果 = 1 モジュールの登録制。検証と SCHEMA はレジストリから生成。
**A.** その設計にしたくなる気持ちはわかる、処理順を厳密に制御できるなら OK。例えば毒と「HP と同じ値だけ攻撃力追加」の装備があったとして、私の一存で「毒の適用前に攻撃力上昇」「毒の適用後に攻撃力上昇」のどちらも実現可能にできていなければならない。

**Q14.** ライフサイクルのフック一覧を先に固定し、全部そこに登録する。
**A.** Q13 の回答に類似で、フック内の処理順を厳密に制御できる必要がある。もしくは、フック内の処理が順序依存を完全に排除できる設計ならそれでも OK。「攻撃後、シールド 2 を追加」「攻撃後、HP を 3 減少」が同時にかかった時、付与順など何か他の要素依存せず常にシールド追加 → HP 減少になるなどの処理順固定が必須。

## D. 状態異常の構造

**Q19.** 共通 6 種と固有はプレイヤー専用、敵は毒だけ。
**A.** OK

**Q20.** 共通はスタック制、固有は残ターン制で上書き。眠りの解除はスタックで表現?
**A.** バステごとが持つ属性としてターン制のものとスタック制のものに分かれる、としましょう。スタック制のものは付与ごとに値が増える、ターン制のものは付与ごとに「付与した効果のターン」で上書きする。4 ターン眠りの状態で、1 ターン眠りを付与すると残ターンが 1 に上書きされる。

**Q21.** 発情 = のろい (heart) の名前替えで効果は同じ。
**A.** OK

**Q22.** 眠りの「行動不能」の意味。
**A.** 「攻撃コマンドを押しても攻撃せず自分の手番をスキップし、即座に相手が行動する」です。

**Q23.** 固有バステの SD は衣装レイヤーごと差し替えか、重ね 1 枚か。衣装との組み合わせ素材は。
**A.** 衣装レイヤーごと差し替えで、固有バステがついてる時には衣装の状態を無視します。衣装による追加効果も固有バステがついてる時には無視する。固有バステの効果が終了したら元の衣装状態に戻ります。固有バステが衣装状態の上位概念として衣装の状態をマスクするイメージです。

**Q24.** statuses テーブルにマスタ化し、敵アクションはステート id を参照。衣装と付随効果も載せる。
**A.** OK
